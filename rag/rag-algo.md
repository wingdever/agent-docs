# 检索增强生成工程算法
工程原则：用轻量算法换取召回广度，再用昂贵算法换取排序精度

## Bi-Encoder（双编码器）
用同一个编码器（共享权重）分别处理查询和文档，
各自生成一个固定长度的向量，再用余弦相似度或内积来衡量远近。

### 可离线预计算：
文档向量在入库时就已算好并建立索引，
查询时只需要编码一次查询向量，然后做近似最近邻搜索。
代价是查询和文档之间没有 token 级别的交互，相关性判断是粗略的，
遇到否定、逻辑约束或精确术语时容易失准。

### 代价
是查询和文档之间没有 token 级别的交互，相关性判断是粗略的，
遇到否定、逻辑约束或精确术语时容易失准。
这正是后续“精排”算法需要弥补的短板。

主流的开源嵌入模型如 BGE 和 E5 都属于 Bi-Encoder 家族，
通过对比学习训练，核心 loss 是 InfoNCE，
目标是把正例在向量空间中拉近、把负例推远。

# 第一阶段：召回算法——在“大”中求“快”
## 向量索引算法：HNSW 与 IVF
暴力扫描全部向量在数据量达到百万级时不可行，必须用近似最近邻（ANN） 索引。两种最主流的算法走了不同的路：
IVF（倒排文件） ：先用 k-means 聚类把向量空间分成若干“桶”，查询时只扫描距离最近的几个桶（由 nprobe 控制）。它用聚类的思路把搜索范围从全体缩小到局部，内存占用较低，但聚类边界处的向量可能被漏掉。
HNSW（分层可导航小世界） ：构建一张多层图，上层稀疏图负责远距离跳跃，底层稠密图负责精细搜索。查询时沿着图的边逐步逼近目标。它的召回质量通常更好，查询延迟更低，代价是内存占用更高。在多数 RAG 场景下，HNSW 是更稳妥的默认选择。

## 词法召回算法：BM25
BM25 是基于词频和逆文档频率的经典稀疏检索算法，擅长精确匹配版本号、错误码、产品名等术语。它的算法逻辑与向量检索完全互补：向量检索捕捉“意思相近但用词不同”，BM25 捕捉“用词精确但语义未必接近”。

## 融合算法：RRF（互易秩融合）
当同时运行 BM25 和向量检索时，两路结果的分数量纲完全不同
（BM25 分数与余弦距离不可直接比较）。
RRF 的算法设计巧妙地绕开了这个问题：它不看原始分数，只看排名。
公式：
RRF_score = 1/(k + rank_from_source_1) + 1/(k + rank_from_source_2)，
常数 k 通常取 60，用于防止单一榜单的头部结果过度主导。
一份文档在两个榜单中都排名靠前则RRF总分就会高于只在单一榜单中靠前的文档。
这就是混合检索在算法层面的“融合规则”。

# 第二阶段：精排算法——在“准”中求“精”
精排只处理召回阶段返回的小规模候选集（通常 20–100 条），可以承受更昂贵的计算。

## Cross-Encoder（交叉编码器）

这是精度最高的重排序算法。它把查询和候选文档拼接在一起送入 Transformer，让查询的每个 token 与文档的每个 token 进行全交叉注意力计算，直接输出一个相关性分数。这种细粒度交互是 Bi-Encoder 不具备的，因此对复杂语义的判断能力最强。

但它的算法特性决定了无法预计算：每条候选文档都需要一次完整的前向传播，延迟可达数百毫秒级别。因此它只适合用在精排阶段，对少量候选做最终裁决。

## ColBERT（延迟交互）

ColBERT 在 Bi-Encoder 和 Cross-Encoder 之间取了一个算法上的折中点。它仍然分别编码查询和文档（文档可以离线算好），但不再把整段文本压成一个向量，而是为每个 token 保留一个向量。打分时，通过 MaxSim 操作计算查询 token 与文档 token 之间的细粒度匹配。

这种“延迟交互”的算法设计，使得 ColBERT 的精度接近 Cross-Encoder，但查询延迟显著更低（约 15–30ms，而 Cross-Encoder 为 50–200ms）。代价是存储开销大——每个文档要存几十到上百个 token 向量，对百万级文档库会消耗大量空间。

# 前置优化：查询改写算法
在召回之前，查询本身的“质量”决定了检索的上限。最常见的改写算法是 HyDE（假设文档嵌入）。

它的算法思路是反直觉的：不直接拿问题去检索，而是让 LLM 先“编造”一段假设性的答案，再用这段假设答案的向量去检索。背后的洞察是：在向量空间中，“问题”和“答案”往往分布在不同的区域，直接拿问题向量去匹配答案文档存在天然的分布错位；而“假设答案”与真实答案在空间中更为接近，匹配效果更好。HyDE 绕开了“查询表述不准确”这一根源性问题，代价是多一次 LLM 调用。

当查询包含多个子问题时，查询分解算法会把复杂查询拆成若干原子子查询，分别检索后再合并结果。

# 如何验证算法选择是否生效：RAGAS 的核心指标算法
引入这些算法后，需要量化判断改动是否真的有效。RAGAS 用 LLM 作为评判器，核心算法逻辑如下：

Faithfulness（忠实度） ：先用 LLM 把生成的答案拆解为若干独立声明，再逐条判断该声明是否能从检索到的上下文中推断出来。这直接暴露“检索到了但模型没用”或“模型编造了上下文没有的内容”。

Context Precision（上下文精确度） ：衡量检索到的相关文档是否被排在更靠前的位置，反映召回与精排的整体排序质量。

把这些指标建立在一个 50–200 条的黄金查询集上，每次调整嵌入模型、索引参数或重排序策略时跑一遍，算法选型就从“凭感觉”变成了“有数据支撑”。

# 算法栈的典型组合
一个经过实践检验的最常见算法栈是：BGE/GTE 嵌入（Bi-Encoder）+ HNSW 向量索引 + BM25 词法召回 + RRF 融合 + Cross-Encoder 精排。如果你的 Markdown 知识库规模不大或对延迟极其敏感，可以先用 HNSW + BGE 跑通，再按需逐层叠加 BM25 和 Cross-Encoder；ColBERT 则适合在需要细粒度匹配、且能接受较高存储成本时作为精排的折中方案引入。
